# 3D design spike: library and bundle budget

Design spike for GitHub issue #23. It answers one question: if MetricFlow adds a 3D view, which approach should every 3D issue (#18 to #22) use, and how much JavaScript may it cost? The answer is CSS 3D by default, with `three` as the only allowed escape hatch, always lazy.

## Measurements

Measured 2026-10-10, outside the repo, with esbuild 0.28.2 (`--bundle --minify --format=esm`, tree-shaking on) and `gzip -c`. Each entry imports the minimum a "one rotating box with one light" needs.

| Option | Version | Minified KB | Gzip KB |
| --- | --- | --- | --- |
| three.js (named imports: WebGLRenderer, PerspectiveCamera, Scene, Mesh, BoxGeometry, MeshStandardMaterial, DirectionalLight) | three 0.186.1 | 523 | 132 |
| react-three-fiber, one `<mesh>`, react and react-dom external | @react-three/fiber 9.8.1 | 908 | 243 |
| react-three-fiber + one drei helper (`OrbitControls` only) | @react-three/drei 10.7.9 | 924 | 248 |
| `<model-viewer>` (`import '@google/model-viewer'`) | @google/model-viewer 4.4.0 | 1054 | 300 |
| CSS 3D | none | 0 | 0 |

Notes on the numbers:

- KB means 1024 bytes. Raw gzip bytes: three 135157, r3f 249249, r3f + drei 254186, model-viewer 307386.
- r3f numbers include `three` and the React reconciler; they are the real cost of the Canvas, not an add-on to the three.js row. Drei was measured with `OrbitControls` only; each further helper adds more.
- `<model-viewer>` also bundles its own three.js. It needs a glTF/GLB asset on top of the 300 KB; MetricFlow has no models.
- Sizes are for a box with a standard material. Loaders, post-processing, text and fonts all add more. Treat the rows as floors.

CSS 3D, no JavaScript:

```css
.scene { perspective: 800px; }
.card  { transform-style: preserve-3d; transform: rotateX(55deg) rotateZ(-20deg); }
.bar   { transform: translateZ(var(--depth)); }
```

## Comparison

| Option | What it can do | Min gzip KB (measured) | SSR story | Accessibility story | Fits "lazy only"? |
| --- | --- | --- | --- | --- | --- |
| CSS 3D | Tilted panels, stacked or extruded bars (boxes made of divs), depth cues. No lighting, no arbitrary meshes. | 0 | Renders on the server as ordinary HTML. | Real DOM: text, focus order, screen readers and `prefers-reduced-motion` work as for 2D. | Not needed, it adds no JS. |
| three.js | Any geometry, lighting, picking, custom shaders. | 132 | Needs `window`, WebGL and a canvas; client only. | Canvas is opaque. Needs a text alternative and keyboard controls built by hand. | Yes, as a dynamic import. |
| react-three-fiber | Same as three.js with a React tree and hooks. | 243 (248 with one drei helper) | Client only (`ssr: false`). | Same as three.js; the canvas is opaque. | Only just; 243 KB is the cost of a convenience layer. |
| `<model-viewer>` | Show and orbit one glTF model, AR on mobile. Not a charting tool. | 300 | Custom element, client only. Poster image can be server rendered. | Built-in `alt` and keyboard orbit, but only for a model. | Yes, but it is the largest and has no data-driven use. |

## How it fits MetricFlow

`PRODUCT.md` says every view should help the engineer rank problems ("Answer what first") and the dashboard must be complete without extras. `DESIGN.md` describes a calm, compact dark console. A spinning showpiece conflicts with both, so:

- 3D is an optional view, off by default. The 2D view is the default, the accessible one, and the one the tests and screenshots cover.
- Every 3D view must show the same ranked data as its 2D twin; it may not hide a number only the 3D view carries.
- Every 3D feature must be gated by the shared guard from issue #21, `use3dEnabled()`. It returns false for reduced motion, low core count, data saver, or no WebGL. Build #21 first; no other 3D issue ships without it.
- No sample or invented data. 3D shows real metrics or an empty state (product principle 1, "Never fake data").

## Recommendation and budget

Pick: CSS 3D for anything that is a tilted panel, a depth-stacked bar or a card flip. If an issue truly needs WebGL (real lighting, a globe), use plain `three` with named imports in a lazy chunk. Do not adopt react-three-fiber or `<model-viewer>`.

Why, from the table:

- CSS 3D costs 0 KB gz and stays server rendered and accessible.
- `three` is 132 KB gz, about 110 KB less than r3f (243 KB) for the same box. The app is a small data console; it does not need a reconciler for one scene.
- `<model-viewer>` is 300 KB gz and shows a model the product does not have.
- The "< 40 KB gz" example in the issue is not reachable with WebGL: three.js alone is more than three times that. The budget below is set from the measurement instead.

Budget:

| Scope | Gzip budget |
| --- | --- |
| Initial bundle (every route, 3D off) | 0 KB added. No import of `three` or any 3D code outside a dynamic import. |
| CSS 3D view | 0 KB JS; at most 2 KB of CSS |
| Lazy `three` chunk (loaded only after the user switches to 3D) | 160 KB gz total (132 KB measured floor + about 28 KB of own code) |

Loading pattern: the 3D component is a Client Component imported with `next/dynamic` and `{ ssr: false }`, rendered only once the user has switched to 3D (`{view === '3d' && <Scene3D />}`) and `use3dEnabled()` is true. Per `node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md` (Next.js 16.3.8 in this repo):

- `next/dynamic` is `React.lazy()` plus Suspense and defers a Client Component's code until it renders.
- By default the lazy component is still prerendered on the server; `ssr: false` turns that off.
- `ssr: false` works only inside a Client Component (`'use client'`); using it in a Server Component is an error.
- A `loading` option shows a placeholder while the chunk loads; use the 2D view as that placeholder so the page never goes blank.

Enforce the budget in review by building and checking the chunk size; add a CI size check only if a 3D feature actually ships.

## Mapping issues #18 to #22

| Issue | Approach | Concern |
| --- | --- | --- |
| #18 | CSS 3D by default | Asks for INP. The dashboard metrics shape has TTFB, LCP and CLS, not INP (INP only appears as an optional column in `lib/tools.ts` when a source supplies it). Use a metric the dashboard collects, or drop INP. |
| #19 | CSS 3D | Targets `DonutChartCard`, which exists in `components/DashboardCharts/` but is not rendered on the dashboard. Retarget a rendered card or first decide to render the donut. |
| #20 | CSS 3D, `three` only if lighting is essential | None found; must pass the same-data-as-2D rule. |
| #21 | Prerequisite: `use3dEnabled()` | Build first. Uses `matchMedia`, `navigator.hardwareConcurrency`, `navigator.connection.saveData` and a WebGL probe, all client side. |
| #22 | `three` lazy chunk if it is a globe | Asks for mock data when New Relic has no region data. That breaks "never fake data". Show an empty state ("No region data from New Relic") instead. |

## Risks and not measured

- Not measured: runtime frame rate, memory, GPU cost, real-device WebGL support, and time to first frame on a slow network.
- Not measured: the app's current bundle, so the "0 KB added" target is not compared against an existing baseline.
- Not measured: gzip versus brotli. Brotli is usually smaller; the budget uses gzip for comparability with the issue.
- Not measured: `three` examples addons (loaders, controls), text rendering, or any drei helper other than `OrbitControls`.
- Numbers are for a bundler (esbuild); Next's Turbopack or webpack output may differ by a few percent.
- Risk: `three` releases change the tree-shaken size; re-measure when upgrading.
- Risk: CSS 3D transforms can blur text and cost layer memory when many cards are promoted; keep the 3D surfaces few.
- Risk: the opaque canvas fails accessibility unless the 2D twin remains one click away and the 3D region has a text summary.
